# Proposta de Spec — Perfil, dashboard, CNPJ secundário e página Sobre

## 1. Ideia / Draft

Esta proposta emenda a **SPEC-018** (perfil da prestadora) e a **SPEC-023** (UI) para entregar:

- área autenticada de **perfil** com edição de dados, troca de e-mail/senha e gestão de CNPJs;
- **dashboard** com resumo de invoices, simulações e clientes;
- **CNPJ secundário** da prestadora, com primário único;
- **página Sobre** própria, com conteúdo distribuído por contexto;
- correção do **design system** que hoje usa tokens inexistentes e quebra os cards;
- remoção de recursos remotos e aplicação de headers de segurança.

A spec **não substitui** as specs 018/023; ela altera apenas os pontos listados.

## 2. Derivação e limites

### 2.1 O que muda

| Tema | Vigente | Proposta |
|------|---------|----------|
| Perfil | somente leitura (`GET /v1/auth/me`) | edição de nome/telefone/e-mail/senha |
| Dashboard | inexistente | `/dashboard` com resumo e atalhos |
| Clientes | inexistente na UI | `/clientes` com CRUD |
| CNPJ da prestadora | um por usuário, `provider_profiles.cnpj` | 1:N em `provider_cnpjs`, até 10 ativos |
| CPF de emissão | inexistente | `provider_profiles.cpf` |
| Categoria da prestadora | `NOT NULL`, só `mei`/`legal_entity` | nullable; `individual`, `mei`, `legal_entity` |
| Sobre | seção `#sobre` na home | página `/sobre` |
| Design tokens | `--space-*`/`--fs-*` usados sem definição | definidos em `:root`, testados |
| Fontes | Google Fonts remoto | pilha local, zero requisição externa |
| Scripts | inline | externalizados em `static/js/` |
| Headers | 3 headers no nginx | CSP, Permissions-Policy, HSTS condicional |
| Navbar | estática (sempre deslogada) | condicional por sessão |

### 2.2 O que não muda

- Sessão e CSRF da SPEC-017.
- Contratos de invoices e clientes das SPEC-019/020.
- Retenção e erase da SPEC-022.
- Invoice bilíngue.
- Isolamento por proprietário (P-14).
- Zero PII em log.

### 2.3 Fora de escopo

- Tema escuro.
- i18n do dashboard (pt-BR apenas; invoice continua bilíngue).
- Notificações em tempo real.
- Upload de avatar.
- Editor de marca/white-label.
- Aplicativo móvel nativo.

## 3. Modelo de dados: documentos de emissão e CNPJ secundário

### 3.1 `provider_profiles`

| Coluna | Hoje | Proposta |
|--------|------|----------|
| `category` | `NOT NULL`, CHECK `('mei','legal_entity')` | nullable; CHECK aceita `individual`, `mei`, `legal_entity` |
| `cpf` | não existe | `CHAR(11) NULL`, documento de emissão do titular |
| `cnpj` | um CNPJ | mantida como espelho depreciado do primário |

```sql
ALTER TABLE provider_profiles ALTER COLUMN category DROP NOT NULL;
ALTER TABLE provider_profiles DROP CONSTRAINT chk_provider_category;
ALTER TABLE provider_profiles
    ADD CONSTRAINT chk_provider_category
    CHECK (category IS NULL OR category IN ('individual', 'mei', 'legal_entity'));

ALTER TABLE provider_profiles ADD COLUMN cpf CHAR(11) NULL;
CREATE UNIQUE INDEX uq_provider_profiles_cpf
    ON provider_profiles (cpf) WHERE cpf IS NOT NULL;
```

Regras:

- `category` nasce `NULL` no cadastro; o cadastro atual fixa `mei` por engano e isso é removido.
- `individual` exige `provider_profiles.cpf` preenchido.
- `mei` e `legal_entity` exigem CNPJ ativo em `provider_cnpjs`.
- Documento de emissão é independente do login: `user_login_identifiers` não é documento de emissão.
- CPF de login, quando informado, é espelhado em `provider_profiles.cpf`; se o usuário tiver CPF de login e nenhum documento de emissão, a migration cria o espelho.

### 3.2 `provider_cnpjs`

```sql
CREATE TABLE provider_cnpjs (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    cnpj CHAR(14) NOT NULL,
    label VARCHAR(80),
    is_primary BOOLEAN NOT NULL DEFAULT FALSE,
    status VARCHAR(16) NOT NULL DEFAULT 'active'
        CHECK (status IN ('active', 'inactive')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_provider_cnpjs_cnpj UNIQUE (cnpj)
);

CREATE UNIQUE INDEX uq_provider_cnpjs_primary
    ON provider_cnpjs (user_id)
    WHERE is_primary AND status = 'active';

CREATE INDEX ix_provider_cnpjs_user ON provider_cnpjs (user_id);
```

### 3.3 Regras

- CNPJ normalizado para 14 dígitos e validado por dígito verificador.
- `cnpj` é imutável após criação; para trocar, criar outro e desativar o antigo.
- Máximo de 10 CNPJs ativos por usuário; acima disso, `422 limit_exceeded`.
- No máximo um primário ativo por usuário.
- O primário não pode ser desativado sem promover outro.
- CNPJ duplicado (global) retorna `409 conflict`.
- CNPJ de outro usuário retorna `404` em qualquer operação.
- `label` é texto livre, 0..80, para diferenciar matriz/filial.

### 3.4 Migração

1. Criar `provider_cnpjs` com `id BIGINT GENERATED BY DEFAULT AS IDENTITY`; DDL sem `identity` não gera id e quebra o backfill.
2. Para cada `provider_profiles.cnpj` não nulo, inserir linha com `is_primary = true`.
3. Importar também CNPJs legados de `user_login_identifiers.kind='cnpj'`, porque o cadastro antigo não gravava `provider_profiles.cnpj` (detalhe em SPEC-024 §7.4). Sem essa fonte, usuário legado perde a capacidade de emitir.
4. Manter `provider_profiles.cnpj` como coluna depreciada, sincronizada com o primário enquanto existir.
5. Se houver CNPJ duplicado entre usuários, a migration falha com relatório; não apagar dados.
6. `downgrade` remove a tabela e restaura `provider_profiles.cnpj` a partir do primário.

## 4. Contrato HTTP: CNPJs da prestadora

### 4.1 `GET /v1/provider/cnpjs`

Sessão obrigatória.

```json
{
  "items": [
    {
      "id": 1,
      "cnpj": "12.345.678/0001-95",
      "label": "Matriz",
      "is_primary": true,
      "status": "active",
      "created_at": "2026-11-17T12:00:00Z"
    }
  ],
  "total": 1
}
```

- CNPJ é exibido mascarado na lista? Não: o titular pode ver o próprio CNPJ completo.
- Em logs, nunca.

### 4.2 `POST /v1/provider/cnpjs`

Sessão + CSRF.

```json
{ "cnpj": "12.345.678/0001-95", "label": "Filial SP", "is_primary": false }
```

- `201` com o CNPJ criado.
- `400` dígito verificador inválido.
- `409` CNPJ já cadastrado.
- `422 limit_exceeded` no limite de 10 ativos.
- Se `is_primary = true`, o primário anterior é rebaixado na mesma transação.

### 4.3 `PUT /v1/provider/cnpjs/{id}`

Sessão + CSRF.

```json
{ "label": "Filial RJ", "is_primary": true, "status": "active" }
```

- `cnpj` não é alterável.
- `is_primary = true` rebaixa o anterior.
- `status = inactive` no primário retorna `409` enquanto não houver outro primário.
- `200` com o CNPJ atualizado.
- `404` cross-owner.

### 4.4 `DELETE /v1/provider/cnpjs/{id}`

- Sessão + CSRF.
- Soft delete (`status = inactive`).
- Primário não pode ser removido sem promoção de outro → `409`.
- `204`.
- `404` cross-owner.

### 4.5 Uso na emissão de invoice

- `issuer_tax_id_digits` de CNPJ deve existir em `provider_cnpjs` **ativo** do titular.
- `issuer_tax_id_digits` de CPF deve existir em `provider_profiles.cpf` do titular.
- Identificador de login (`user_login_identifiers`) não autoriza emissão.
- CNPJ inativo ou de outro usuário → `403 issuer_not_allowed`.
- Clone de invoice com emissor inativo → `409 issuer_inactive`; a invoice original permanece.
- A invoice guarda o snapshot do CNPJ usado; mudanças posteriores no cadastro não alteram invoices antigas.
- Correção de CNPJ com invoice finalizada mantém o CNPJ antigo como `inactive` e adiciona o novo.

## 5. Perfil e dashboard

### 5.1 Rotas de frontend

| Rota | Auth | Conteúdo |
|------|------|----------|
| `/dashboard` | sim | resumo, últimas invoices, últimas simulações, clientes, pendências |
| `/perfil` | sim | dados pessoais, segurança, CNPJs, estado da conta |
| `/clientes` | sim | lista, busca, criação, edição, ativação/inativação |
| `/sobre` | não | página institucional |

### 5.2 Guarda de sessão

- O frontend chama `GET /v1/auth/me` repassando os cookies da requisição.
- `200` → renderiza com `me` no contexto.
- `401` → `302` para `/auth/login?next=<path>`.
- `403 profile_incomplete` → `302` para `/perfil/completar`.
- Nenhuma rota protegida renderiza HTML antes de validar a sessão.
- O `next` é validado como caminho interno (começa com `/`, não `//`).

### 5.3 Dashboard

Cards de resumo:

| Card | Fonte | Cálculo |
|------|-------|---------|
| Invoices em draft | `GET /v1/invoices?status=draft&limit=1` | `total` |
| Invoices finalizadas | `GET /v1/invoices?status=finalized&limit=1` | `total` |
| Clientes ativos | `GET /v1/clients?status=active&limit=1` | `total` |
| Simulações | `GET /v1/simulations?limit=5` | `total` do envelope |

Listas:

- últimas 5 invoices com número, cliente, status, valor e ação (abrir PDF);
- últimas 5 simulações com moeda, regime, valor e data;
- clientes com atalho para `/clientes`;
- pendências: e-mail ausente, CNPJ primário ausente, perfil incompleto.

Regras:

- Nenhum endpoint de agregação novo; o frontend compõe os dados.
- Todas as listas usam o envelope `{items,total,limit,offset}`; o contador vem de `total`, nunca do tamanho de `items`.
- Se uma chamada falhar, o card mostra estado de erro isolado; a página não quebra.
- Todos os valores vêm de recursos do próprio usuário.
- Estado vazio tem CTA (ex.: "Cadastrar primeiro cliente", "Emitir invoice").

### 5.4 Perfil

Seções:

1. **Dados pessoais**: nome, e-mail, telefone; edição via `PATCH /v1/auth/me`.
2. **Segurança**: troca de e-mail (`PUT /v1/auth/me/email`) e senha (`PUT /v1/auth/me/password`), com senha atual.
3. **Identificadores**: e-mail, CPF/CNPJ de login mascarados; imutáveis.
4. **Documentos de emissão**: CPF do titular (`provider_profiles.cpf`) e lista de CNPJs; adicionar secundário, editar label, promover a primário, desativar.
5. **Categoria da prestadora**: `individual`, `mei` ou `legal_entity`; `individual` exige CPF de emissão, as demais exigem CNPJ ativo.
6. **Estado da conta**: ativo/dormente, data de criação, link para exclusão (SPEC-022).

Regras:

- Formulários com validação client-side e server-side.
- Toda mutação envia `X-CSRF-Token`; logout também.
- Erros por campo com `aria-live="polite"`.
- Sucesso com mensagem não intrusiva.
- Nunca exibir hash, token ou valor completo de CPF/CNPJ de login.
- Identificadores de login não são editáveis aqui; documentos de emissão são.
- Após troca de e-mail/senha, atualizar a sessão e a navbar.

### 5.5 Navbar e logout

Visitante:

```text
Início | Emitir Invoice | Sobre | Entrar | Cadastre-se
```

Autenticado:

```text
Início | Emitir Invoice | Dashboard | Clientes | Sobre | Perfil | Sair
```

- `Sair` envia `POST /v1/auth/logout` com `X-CSRF-Token` e redireciona para `/`.
- O menu mobile usa o mesmo estado.
- A navbar não pode "piscar" entre estados; o servidor renderiza o estado correto.

## 7. Design system e correção visual

### 7.1 Tokens obrigatórios

`app-ifit.css` passa a definir:

```css
:root {
  --space-1: 4px;
  --space-2: 8px;
  --space-3: 12px;
  --space-4: 16px;
  --space-5: 20px;
  --space-6: 24px;
  --space-8: 32px;
  --space-12: 48px;
  --space-16: 64px;

  --fs-xs: 0.75rem;
  --fs-sm: 0.875rem;
  --fs-base: 1rem;
  --fs-lg: 1.125rem;
  --fs-xl: 1.25rem;
  --fs-2xl: 1.5rem;
  --fs-3xl: 1.875rem;
  --fs-4xl: 2.25rem;

  --radius-sm: 8px;
  --radius-md: 12px;
  --radius-lg: 16px;
  --radius-full: 9999px;

  --line-tight: 1.2;
  --line-normal: 1.5;
  --line-relaxed: 1.65;
}
```

Nenhum `var(--space-*)` ou `var(--fs-*)` pode ficar sem definição.

### 7.2 Cards

- Card é `display: flex; flex-direction: column;`.
- `height: 100%` dentro do grid.
- `padding: var(--space-6)`.
- `gap: var(--space-3)` entre título, texto e ação.
- `min-width: 0` para evitar overflow.
- Não aninhar card dentro de card.
- Ação no rodapé com `margin-top: auto`.
- Grid: `repeat(auto-fit, minmax(260px, 1fr))`.
- Em 360 px: uma coluna; em 768 px: duas; em 1280 px: três ou quatro conforme a seção.
- Alturas iguais por linha; diferença máxima de 1 px.

### 7.3 Tipografia

- Família: `Inter, system-ui, -apple-system, "Segoe UI", Roboto, sans-serif`.
- Sem `@import` remoto e sem `<link>` para Google Fonts.
- Títulos com `line-height: var(--line-tight)`.
- Corpo com `line-height: var(--line-normal)`.
- Máximo de 75 caracteres por linha em textos longos.

### 7.4 Responsividade

Viewports de aceite:

| Viewport | Regra |
|----------|-------|
| 360×800 | uma coluna; navbar em menu; sem scroll horizontal |
| 768×1024 | duas colunas; cards alinhados |
| 1280×800 | três/quatro colunas; largura máxima 1200 px |
| 1440×900 | mesma de 1280, com respiro |

Teste objetivo:

- `document.documentElement.scrollWidth <= window.innerWidth`.
- Nenhum elemento com `getBoundingClientRect().right > innerWidth`.
- `padding` computado de `.card` ≥ 16 px.
- Cards da mesma linha com altura igual (`±1 px`).

### 7.5 Acessibilidade

- WCAG 2.2 AA.
- Contraste ≥ 4.5:1 para texto normal; ≥ 3:1 para grande.
- Foco visível em todos os controles.
- `label` associado a `input`.
- Erros com `role="alert"` e `aria-live="polite"`.
- Navegação por teclado completa.
- `prefers-reduced-motion` respeitado.
- Ícones decorativos com `aria-hidden="true"`.
- Skip link para o conteúdo principal.

## 8. Segurança de frontend e infra

### 8.1 Scripts

- Remover `onclick` inline.
- Mover `<script>` de `login.html`, `register.html` e `invoice_form.html` para `static/js/`.
- Nenhum `eval`, `new Function` ou `innerHTML` com dados do usuário.
- Dados dinâmicos via `textContent` ou `dataset`.

### 8.2 Headers no proxy

```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'self'; object-src 'none'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: no-referrer
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()
```

- HSTS somente quando TLS estiver ativo: `Strict-Transport-Security: max-age=31536000; includeSubDomains`.
- `style-src 'unsafe-inline'` é débito temporário; migrar estilos inline para classes.
- CSP em modo `Report-Only` por 7 dias antes de bloquear, com relatório local.

### 8.3 Cookies e TLS

- Produção exige HTTPS no proxy.
- `session` e `csrf_token`: `Secure` em produção.
- `csrf_token` não é HttpOnly (o frontend precisa ler).
- `session` é HttpOnly.
- `SameSite=Lax`.
- `COGME_ENV=development` permite `Secure=false` apenas para `localhost`.

### 8.4 LGPD

- Dashboard mostra apenas dados do próprio usuário.
- Nenhum dado de cliente é enviado a terceiros.
- Zero recursos remotos (fontes, analytics, CDN).
- Logs de frontend não contêm PII.
- Perfil permite corrigir dados e excluir conta (SPEC-022).

- **AC-026-23** Migration cria `provider_cnpjs` com `id` identidade e importa CNPJs de `provider_profiles.cnpj` e de `user_login_identifiers.kind='cnpj'`.
- **AC-026-24** Clone de invoice com emissor inativo retorna `409 issuer_inactive`; original preservada.
- **AC-026-25** Toda mutação do perfil envia `X-CSRF-Token`; sem header, resposta é `403`.
- **AC-026-26** Contadores do dashboard vêm de `total` do envelope; listas truncadas em `limit` não zeram o contador.
